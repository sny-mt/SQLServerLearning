# 演習 23 — 待機統計とボトルネック特定

対象解説: [docs/23_wait_statistics.md](../docs/23_wait_statistics.md)
使用DB: `SalesLearning`(先頭で `USE SalesLearning;` を実行しておくこと)

> **この演習は「クエリの結果が合っているか」ではなく、
> 「数字を見て何を疑い、次に何を見るかを言えるか」を問う演習**です。
> 各問、**必ず自分の環境の実測値をメモしながら**進めてください。
> 解答例 [solutions/23_wait_statistics.sql](solutions/23_wait_statistics.sql) と照合しましょう。

## この演習の前提

1. **`VIEW SERVER STATE` 権限**があること(開発機の `sysadmin` なら問題ありません)。
2. `sample-db/03_bulk_data.sql` を実行し、**`dbo.OrdersBig`(100万行)** が作成済みであること。
3. **`dbo.OrdersBig` に非クラスタ化インデックスが1本も無い状態**であること
   ([18 章](../docs/18_indexes_execution_plans.md) の Q13 後片付けを済ませた状態)。
   インデックスが無いからこそ大きなスキャンが発生し、待機が観測できます。
4. `sample-db/05_workload.sql` の **【準備】セクション**(冒頭)を1回だけ実行し、
   **`dbo.WorkloadTest`(1000行)** を作成しておくこと。

## SSMS のウィンドウ構成(Q5 以降で使います)

**クエリウィンドウを5枚開いてください。** 以降、次の名前で呼びます。

| ウィンドウ | 役割 | 流すもの |
|---|---|---|
| **W1** | 負荷(読み取り) | `05_workload.sql` セクションA |
| **W2** | 負荷(読み取り) | `05_workload.sql` セクションA(2本目) |
| **W3** | 負荷(書き込み) | `05_workload.sql` セクションB |
| **W4** | 観測(瞬間) | `05_workload.sql` セクションE / `sys.dm_os_waiting_tasks` |
| **W5** | **計測(差分)** | スナップショット①→②→③ |

> ⚠️ **`05_workload.sql` の各セクションはブロックコメント `/* ... */` で囲まれています。**
> 実行するときは **中身だけを選択して `F5`**(または該当ウィンドウにコピーしてコメントを外す)。
> どのセクションにも **時間制限(60秒 / 30秒)があり、放置しても自動で止まります**。

> ⚠️ **`DBCC SQLPERF('sys.dm_os_wait_stats', CLEAR)` を扱う問題(Q12)があります。**
> これは **インスタンス全体の累計をゼロにし、元に戻せません**。
> **自分専用の開発機でだけ実行**してください。共有サーバー・本番では絶対に実行しないこと。

> ⚠️ **最後に Q13 の後片付けまで必ず実行してください。**
> 特に **セクションC を途中で止めた場合、トランザクションが開いたままロックを保持し続けます**。

## 基礎

**Q1.** このインスタンスの **SQL Server サービス起動時刻** と **稼働時間(時間・日数)** を取得しなさい。
そのうえで、「`sys.dm_os_wait_stats` の値をそのまま眺めることの問題点」を、
取得した稼働時間の数字を使って説明しなさい。
(ヒント: `sys.dm_os_sys_info`)

**Q2.** `sys.dm_os_wait_stats` を **フィルタなしで** `wait_time_ms` の降順に上位10件表示しなさい。
出てきた待機タイプのうち **「性能とは無関係なもの(アイドル待機)」がどれか** を挙げ、
なぜそれらが上位に来るのかを説明しなさい。

**Q3.** Q2 に **アイドル待機の除外フィルタ**を追加し、さらに次の列を計算して上位15件を表示しなさい。

- **リソース待機ms**(SUSPENDED で待った時間)
- **シグナル待機ms**(RUNNABLE で待った時間)
- **平均待機ms**(1回あたり)
- **全体に占める割合(%)** と **累積割合(%)**

そのうえで、**累積割合が 80% を超えるまでの待機タイプ**を書き出しなさい。
(ヒント: 割合は `SUM(...) OVER ()`、累積は `SUM(...) OVER (ORDER BY ... ROWS UNBOUNDED PRECEDING)`)

**Q4.** インスタンス全体の **シグナル待機の比率(%)** を1行で求めなさい。
その値から **CPU が圧迫されているかどうか**を判断し、
判断の根拠になる別の DMV の列も併せて確認しなさい。
(ヒント: `sys.dm_os_schedulers` の `runnable_tasks_count`)

**Q5.** **`wait_time_ms` と「リソース待機」の関係を式で書きなさい**。
そのうえで、次の2つのケースについて「打ち手の方向がどう変わるか」を答えなさい。

1. `PAGEIOLATCH_SH` の `wait_time_ms` が 100万ms、`signal_wait_time_ms` が 5万ms
2. `PAGEIOLATCH_SH` の `wait_time_ms` が 100万ms、`signal_wait_time_ms` が 70万ms

## 応用 — 実際に負荷を掛けて測る

ここからは **05_workload.sql** を使います。上の「ウィンドウ構成」を先に用意してください。

**Q6.**(読み取り負荷)次の手順で **スナップショット差分** を取り、
**その60秒間に支配的だった待機タイプ**を特定しなさい。

1. **W5** で開始スナップショットを一時テーブル `#WaitSnapshot` に保存する
2. すぐに **W1** → **W2** でセクションA(読み取り負荷・60秒)を起動する
3. 60秒待つ(W5 で `WAITFOR DELAY '00:01:00';` でもよい)
4. **W5** で差分を計算し、上位15件を表示する

差分の結果には、次の列を必ず含めること。

- 待機タイプ / 待機回数 / 合計待機ms / リソース待機ms / シグナル待機ms / 平均待機ms
- **割合(%)**
- **待機秒毎秒**(= 合計待機ms ÷ 経過ms。「常時何本のスレッドが待っていたか」)

**Q7.** Q6 の結果について、次に答えなさい。

1. 1位の待機タイプは何か。それは **リソース待機とシグナル待機のどちらが主体**か。
2. その待機タイプが上位なら **何を疑い、次にどの DMV / 指標を見るべき**か。
3. `PAGEIOLATCH_SH` がほとんど出ず `SOS_SCHEDULER_YIELD` が支配的だった場合、
   **それはなぜか**、また **CPU を増設すべきか**を説明しなさい。

**Q8.**(書き込み負荷)Q6 と同じ手順で、今度は **W3** でセクションB(書き込み負荷・60秒)を実行し、
差分を取りなさい。読み取り負荷のときと **支配的な待機タイプがどう変わったか** を比較し、
その待機タイプについて「疑うこと」と「次に見るもの」を述べなさい。

**Q9.**(ブロッキング)次の手順でブロッキングを **意図的に発生させ**、犯人を特定しなさい。

1. **W3** でセクションC(ブロッカー・30秒ロック保持)を実行する
2. **すぐに W1** でセクションD(ブロックされる側)を実行する — 返ってこないことを確認
3. **W4** で `sys.dm_os_waiting_tasks` を使い、
   **待っているセッション・待機タイプ・`blocking_session_id`・`resource_description`** を表示する
4. さらに **ブロックしている側**が何を実行したのかを調べる
5. 30秒経つとセクションC は自動でロールバックし、W1 の結果が返ってくることを確認する

観測できた待機タイプの名前と、それが 4 節のどの分類に当たるかを答えなさい。
(ヒント: `sys.dm_exec_input_buffer`(2016+)または `sys.dm_exec_sql_text`)

**Q10.**(ファイル I/O の裏取り)`PAGEIOLATCH_*` や `WRITELOG` が上位に来たときの
**裏取り用クエリ**を書きなさい。データベースファイルごとに
**読み取り1回あたりの平均ミリ秒**と**書き込み1回あたりの平均ミリ秒**を出し、
`SalesLearning` の **データファイル(ROWS)とログファイル(LOG)** の値を比較しなさい。
どのくらいの値なら「遅い」と判断するか、目安も述べること。
(ヒント: `sys.dm_io_virtual_file_stats(NULL, NULL)` と `sys.master_files`)

## チャレンジ

**Q11.**(セッション単位の計測)`sys.dm_exec_session_wait_stats`(**2016+**)を使って、
**1本のクエリだけの待機**を測りなさい。

1. 実行直前に自分のセッションの待機統計を `#Before` に保存する
2. 次のクエリを実行する
   ```sql
   SELECT Status, COUNT(*) AS 件数, SUM(Amount) AS 合計
   FROM   dbo.OrdersBig
   GROUP  BY Status;
   ```
3. 差分を取り、このクエリが何を待ったかを表示する

そのうえで、**`sys.dm_os_wait_stats` ではなく `sys.dm_exec_session_wait_stats` を使う利点**を
2つ挙げなさい。また、このビューの **注意点(いつリセットされるか)** も述べなさい。

**Q12.**(待機タイプの読み分け)次の8つのシナリオについて、
**① 何を疑うか**、**② 次に見る DMV / 指標**、**③ 代表的な打ち手** をそれぞれ答えなさい。
(SQL は不要。文章で答えること)

1. `PAGEIOLATCH_SH` が全体の 60%。平均待機 25ms。シグナル待機は全体の 5%。
2. `WRITELOG` が全体の 45%。待機回数が 800万回、平均待機 0.4ms。
3. `LCK_M_S` が全体の 50%。待機回数は 120 回だが `max_wait_time_ms` が 45,000。
4. `SOS_SCHEDULER_YIELD` が全体の 40%。待機回数 3,000万回、平均待機 0.02ms。
5. `RESOURCE_SEMAPHORE` が上位に出現している。
6. `PAGELATCH_UP` が上位。`resource_description` が `2:1:1` や `2:1:3`。
7. `ASYNC_NETWORK_IO` が全体の 55%。
8. `THREADPOOL` が出現しており、新規接続もできない。

**Q13.**(累計のリセットと後片付け ― **必須**)

1. **`DBCC SQLPERF('sys.dm_os_wait_stats', CLEAR)` を実行すると何が起きるか**を、
   **影響範囲**・**元に戻せるか**・**必要な権限**の3点で説明しなさい。
   また、**本番環境でこれを使わずに「今」を診断する方法**を答えなさい。
2. (**自分専用の開発機の場合のみ**)実際に CLEAR を実行し、
   直後に `sys.dm_os_wait_stats` の合計がほぼ 0 になることを確認しなさい。
   共有環境では **実行せず、コメントのまま読むだけ**にすること。
3. **後片付け**: `@@TRANCOUNT` が 0 であることを全ウィンドウで確認し、
   `dbo.WorkloadTest` を削除しなさい。`#WaitSnapshot` / `#Before` も削除すること。

**Q14.**(総合)ここまでの計測結果をもとに、
**「このサーバーの待機プロファイル報告書」** を箇条書きで書きなさい。最低限、次を含めること。

- 計測方法(累計か差分か。差分ならその期間)
- 上位3件の待機タイプと、それぞれの割合・平均待機ms・リソース/シグナルの内訳
- そこから導かれる **ボトルネックの仮説**
- **次に実施する調査**(どの章・どの DMV に進むか)
- **待機統計だけでは分からないこと**(なぜ Query Store や `sys.dm_exec_query_stats` が必要か)
