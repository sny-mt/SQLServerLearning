# 演習 31 — パーティショニング

対象解説: [docs/31_partitioning.md](../docs/31_partitioning.md)
使用DB: `SalesLearning`(先頭で `USE SalesLearning;` を実行しておくこと)

> **この演習は `sample-db/04_analytics_data.sql` を実行して `dbo.SalesFact`(1000万行)を
> 作成済みであることが前提** です。まだなら先に実行してください(1〜3分ほどかかります)。
> 重い環境ではスクリプト内の `@Total` を `2000000` に減らして構いません
> (行数が減っても、この演習の学びは変わりません)。

各問、**まず自力でSQLを書いて実行** → 結果を確認 → 解答例
[solutions/31_partitioning.sql](solutions/31_partitioning.sql) と照合しましょう。
解答例と書き方が違っても、同じ結果になっていれば正解です。

**この章の演習は「作れたか」ではなく「区画がどう変化したか・何秒かかったか」まで見て
はじめて正解**です。作業を始める前に次を必ず有効にしてください。

- SSMS で `Ctrl` + `M`(**実際の実行プランを含める**)を ON にする
  → `Actual Partition Count` は **実際の実行プランにしか出ません**
- `SET STATISTICS TIME ON;` を実行しておく(`SWITCH` の速さを数字で見るため)

次のような表にメモしながら進めると学習効果が高いです。

| 問 | 操作 | Actual Partition Count | 経過時間 |
|---|---|---|---|
| Q9-a | `WHERE SaleDate` 範囲指定 | 1 | … |

## 基礎

**Q1.**(考えるだけ・SQLは不要)
同僚から「`dbo.SalesFact` が1000万行あって遅いので、パーティショニングしたい」と相談されました。
**この相談への正しい返答**を、次の観点で述べなさい。

1. パーティショニングの主目的は何か。性能はどう位置づけられるか。
2. 「遅い」を解決するために、パーティショニングより先に検討すべきことは何か(2つ以上)。
3. 逆に、どんな要件が出てきたらパーティショニングを採用すべきか。

**Q2.** `dbo.SalesFact` の総行数・`SaleDate` の最小/最大を確認し、さらに
**年ごとの行数**を一覧しなさい。
(ヒント: `YEAR(SaleDate)` で `GROUP BY`。ここは全件集計なので SARGability は気にしなくてよい)

**Q3.** `SaleDate`(`DATE` 型)を **`RANGE RIGHT`** で **年単位**に区切る
パーティション関数 `pf_SalesByYear` を作りなさい。境界値は
`'2015-01-01'` から `'2025-01-01'` までの **各年1月1日(11個)** とすること。

作成後、次に答えなさい。

1. 区画はいくつできたか。境界値の個数との関係は。
2. `'2015-01-01'` と `'2025-01-01'` を境界に含めたことで、**わざと空になる区画**が2つできる。
   それはどこか。なぜわざとそうするのか。
3. `RANGE LEFT` にしていたら、`2016-01-01` の行はどの区画に入っていたか。
   日付分割で `RANGE RIGHT` が定石とされる理由を2つ挙げなさい。

(ヒント: `sys.partition_functions` と `sys.partition_range_values` で確認できる)

**Q4.** 全区画を `[PRIMARY]` ファイルグループに置くパーティションスキーム
`ps_SalesByYear` を作りなさい。作成後、区画番号とファイルグループの対応を一覧しなさい。
(ヒント: `sys.partition_schemes`・`sys.destination_data_spaces`・`sys.filegroups`)

**Q5.** `dbo.SalesFact` と **同じ列構成**のパーティション表 `dbo.SalesFactPartitioned` を、
`ps_SalesByYear (SaleDate)` 上に作りなさい。主キーは
`PK_SalesFactPartitioned` という名前のクラスタ化主キーとする。

そのうえで次を確認しなさい。

1. **まず `PRIMARY KEY CLUSTERED (SaleId)` だけで作ろうとして、エラーを実際に出す。**
   エラーメッセージを読み、**なぜパーティション列を含めなければならないのか**を説明する。
2. `(SaleId, SaleDate)` に直して作成する。
3. この主キーによって「`SaleId` 単独の一意性」は保証されるか。されないなら、
   それは実務上どういうリスクで、どう対処し得るか。

## 応用

**Q6.** `dbo.SalesFact` の全行を `dbo.SalesFactPartitioned` にコピーしなさい。
**1文でまとめて `INSERT` せず、年単位のループで投入**すること。
なぜ分割するのかも述べなさい。
(ヒント: `WHILE` ループ + `DATEFROMPARTS`。`WITH (TABLOCK)` も付けてみる)

**Q7.** `$PARTITION` 関数を使って、**区画ごとの行数・最古日・最新日**を一覧しなさい。
そのうえで次に答えなさい。

1. 区画番号と年の対応表を作りなさい(区画2 = 2015年、…)。
2. 行数 0 の区画はいくつあるか。それは Q3-2 で予想したものと一致するか。
3. `$PARTITION.pf_SalesByYear('2018-07-15')` は何を返すか。**表を読まずに**確認しなさい。

**Q8.** Q7 と同じ「区画ごとの行数」を、**カタログビューだけ**から取得しなさい。
下限値・上限値・ファイルグループ名も一緒に表示すること。
Q7 の `$PARTITION` 版と **実行時間を比較**し、差がなぜ生まれるのかを説明しなさい。
(ヒント: `sys.partitions` の `rows` 列。`index_id IN (0, 1)` で絞る)

**Q9.** **パーティション除外**を実行プランで確認します。
次の3つを `Ctrl`+`M` を ON にして実行し、それぞれの
**`Actual Partition Count`** を記録して比較しなさい。

- **a.** `WHERE SaleDate >= '2018-01-01' AND SaleDate < '2019-01-01'` で件数と `Amount` 合計
- **b.** `WHERE CustomerId = 500` で件数と `Amount` 合計
- **c.** `WHERE YEAR(SaleDate) = 2018` で件数と `Amount` 合計(a と結果は同じはず)

そのうえで:

1. a と c は同じ結果を返すのに `Actual Partition Count` が違う。**なぜか**。
2. b を速くしたいとき、パーティショニングは答えになるか。ならないなら何が答えか。
3. `Actual Partition Count` はプランのどこで見るか、手順を書きなさい。
4. (発展)日付をリテラルではなく **ローカル変数** に入れて a を実行すると、除外は効くか。
   推定行数はどうなるか。

**Q10.**(発展)`WHERE SaleId = 5000000` の1行を取り出し、`Actual Partition Count` を見なさい。
値がいくつになるかを **予想してから** 実行し、**なぜそうなるのか** を説明しなさい。
これは「パーティショニングによって遅くなる」典型例です。同じ条件のクエリを
`dbo.SalesFact`(分割していない側)でも実行し、論理読み取り数を比較しなさい。

**Q11.** **スイッチアウト**で 2015年のデータを一瞬で切り離しなさい。

1. 受け皿 `dbo.SalesFactArchive2015` を作る
   (**構造は完全に同じ・`[PRIMARY]` 上・パーティション化しない**)。
2. 2015年の区画を `SWITCH` で付け替える。**経過時間を記録**すること。
3. 切り離し後、`dbo.SalesFactPartitioned` の区画別行数と、
   `dbo.SalesFactArchive2015` の行数を確認する。
4. わざと **列の NULL 許容を1つ変えた受け皿** を作って `SWITCH` してみて、
   どんなエラーになるか確認しなさい(`SWITCH` の前提条件の厳しさを体感すること)。
5. 同じことを `DELETE` でやったら何が起きるか。
   **`BEGIN TRAN` … `ROLLBACK` で囲んで** 2016年ぶんを `DELETE` してみて、経過時間を比較しなさい
   (実行が重いと感じたら、実行せず考察だけでもよい)。

(ヒント: 区画番号は決め打ちせず、`$PARTITION.pf_SalesByYear('2015-06-01')` で求めるとよい)

## チャレンジ

**Q12.** **スライディングウィンドウ**の前半(古い側の片付け)を実行しなさい。

1. Q11 で空になった 2015年の区画と、その左隣の空区画を `MERGE` で1つにまとめなさい。
   **`MERGE RANGE` に渡すのは区画番号ではなく境界値**である点に注意。
2. `MERGE` 後、区画の総数と各区画の番号がどう変わったかを確認しなさい。
   **区画番号が繰り上がる**ことを実際に目で見ること。
3. ここから「保守スクリプトで区画番号をハードコードしてはいけない」理由を述べなさい。

**Q13.** **スライディングウィンドウ**の後半(新しい側の追加)を実行しなさい。

1. `SPLIT` で 2025年用の区画を作りなさい。**`SPLIT` の前に必要な準備が1つあります**。
   それを忘れて `SPLIT` を実行し、**エラーを実際に出してから**正しくやり直すこと。
2. なぜ「末尾の **空の** 区画」を割るのが重要なのか説明しなさい。
   もし末尾の区画に100万行入っていたら何が起きるか。
3. ステージング表 `dbo.SalesFactStage2025` を作り、2025年の行を3件だけ入れて、
   **スイッチイン**で `dbo.SalesFactPartitioned` に接続しなさい。
   - **まず CHECK 制約を付けずに `SWITCH` を実行し、エラーを出すこと。**
     エラーメッセージから **CHECK 制約が必要な理由** を説明する。
   - 次に正しい CHECK 制約を付けて成功させる。
     **境界の書き方(`BETWEEN` ではなく半開区間)** に注意。
4. スイッチイン後、区画別行数で 2025年の区画に3行入っていることを確認しなさい。
5. ①〜④の一連の流れを「毎年末に回す定型作業」として整理し、
   **すべてメタデータ操作で済むのはどの手順か**を挙げなさい。

**Q14.**(保守と設計判断)

1. `sys.dm_db_index_physical_stats` を使って、`dbo.SalesFactPartitioned` の
   **区画別の断片化率とページ数**を一覧しなさい。
2. 直近の区画(2024年)だけをインデックス再構築しなさい。
   全区画を再構築するのと比べて、何が嬉しいのか述べなさい。
3. この表に **インクリメンタル統計** を有効にしなさい。
   有効にすると何が速くなり、**何は速くならない/変わらない**のかを述べなさい。
4. (考察のみ)この表に **クラスタ化列ストアインデックス** を併用するとしたら、
   **年単位・月単位・日単位**のどの粒度にすべきか。
   1000万行という規模と「ロウグループは区画をまたげない」という制約から、
   数字を挙げて根拠を述べなさい。

**Q15.**(**必須の後片付け**)この演習で作成したオブジェクトをすべて削除し、
`SalesLearning` を演習前の状態に戻しなさい。

1. **まず、わざと順序を間違えて** `DROP PARTITION FUNCTION pf_SalesByYear;` を実行し、
   エラーメッセージを読みなさい。次に `DROP PARTITION SCHEME ps_SalesByYear;` も実行し、
   これもエラーになることを確認しなさい。
2. **正しい順序**で削除しなさい。順序と、その順序でなければならない理由を述べなさい。
3. 削除後、`sys.partition_functions` / `sys.partition_schemes` / `sys.objects` を確認し、
   何も残っていないことを確かめなさい。
4. `dbo.SalesFact` が **手つかずで1000万行のまま** であることを確認しなさい。

(ヒント: `DROP ... IF EXISTS` は **SQL Server 2016+**。
`DROP PARTITION SCHEME` / `DROP PARTITION FUNCTION` にも使えます)
