# 演習 26 — DMV による調査

対象解説: [docs/26_dmv_investigation.md](../docs/26_dmv_investigation.md)
使用DB: `SalesLearning`(先頭で `USE SalesLearning;` を実行しておくこと)

> **この演習は次の2つが前提**です。まだなら先に実行してください。
> - `sample-db/03_bulk_data.sql` … `dbo.OrdersBig`(100万行)を作成
> - `sample-db/05_workload.sql` … **【準備】セクションを1回だけ実行**して `dbo.WorkloadTest` を作成

各問、**まず自力でクエリを書いて実行** → 結果を確認 → 解答例
[solutions/26_dmv_investigation.sql](solutions/26_dmv_investigation.sql) と照合しましょう。
解答例と書き方が違っても、同じ結果になっていれば正解です。

## この演習の進め方(必ず読むこと)

**DMV は「何かが動いていないと何も見えません」。** SSMS のクエリウィンドウを
**最低4つ**開いて、次の役割を割り当ててください。

| ウィンドウ | 役割 | 流すもの |
|---|---|---|
| **W1** | 読み取り負荷 | `05_workload.sql` の **セクションA** |
| **W2** | 読み取り負荷(2本目) | `05_workload.sql` の **セクションA** |
| **W3** | 書き込み負荷 / ブロッカー | `05_workload.sql` の **セクションB** または **セクションC** |
| **W4** | **観測用** | この演習のクエリを書く |

- セクションA・B は **60秒**、セクションC は **30秒**で自動停止します。
  時間切れになったら **もう一度実行**してから観測クエリを流してください。
- 観測クエリはすべて **W4** で実行します。W4 では負荷を流さないこと。

> ⚠️ **Q17 の後片付けまで必ず実行してください。** この演習では非クラスタ化インデックスを作ります。
> 残したままにすると 18 章など他の演習の計測結果が変わります。

> ⚠️ **`DBCC FREEPROCCACHE`(引数なし)は、この演習でも実行しません。**
> 学習環境であっても、範囲を限定したクリア方法を身に付けることが目的です(Q15)。

## 基礎

**Q1.** 調査を始める前の「作法」として、**この SQL Server がいつ起動したか** と
**現在までの稼働時間(時間・分)** を取得しなさい。
そのうえで、**なぜ DMV を読む前に必ずこれを確認しなければならないのか** を、
`sys.dm_exec_query_stats` と `sys.dm_db_index_usage_stats` を例に説明しなさい。
(ヒント: `sys.dm_os_sys_info`)

**Q2.** W1・W2 でセクションA(読み取り負荷)を実行した状態で、
**今実行中のユーザーリクエストの一覧** を取得しなさい。次の情報をすべて含めること。

- セッションID / ログイン名 / ホスト名 / アプリ名 / 対象DB
- 状態(`status`)/ 待機タイプ / 待機時間 / ブロック元セッションID
- CPU時間 / 経過時間 / 論理読み取り数
- **実行中の SQL 本文**

自分自身のセッションとシステムセッションは除外すること。
(ヒント: `sys.dm_exec_requests` + `sys.dm_exec_sessions` + `sys.dm_exec_sql_text`、`@@SPID`、`is_user_process`)

**Q3.** Q2 の結果に出ている実行中クエリについて、**実行プランを取得**しなさい。
`sys.dm_exec_query_plan` と `sys.dm_exec_text_query_plan` の **両方**で取得し、
**戻り値の型と使いどころの違い**を説明しなさい。

**Q4.** `dbo.OrdersBig` に現在存在するインデックスについて、
**シーク回数・スキャン回数・ルックアップ回数・更新回数** と **最終使用日時** を一覧しなさい。
`PK_OrdersBig` しかない状態でも **1行は必ず表示されること**。
(ヒント: `sys.indexes` を主にして `sys.dm_db_index_usage_stats` を **`LEFT JOIN`**。
なぜ `INNER JOIN` ではいけないのか答えなさい)

**Q5.** `sys.dm_exec_query_stats` から、**CPU 合計時間の上位10クエリ** を取得しなさい。
実行回数・CPU合計(ms)・CPU平均(ms)・経過平均(ms)・論理読み取り合計・
プラン作成時刻・最終実行時刻を含めること。
**`total_worker_time` の単位に注意**すること。

## 応用

**Q6.** Q5 のクエリには問題があります。`sys.dm_exec_sql_text` が返す `text` は
**バッチ全体**なので、複数ステートメントを含むバッチでは「どの1文が重いのか」が分かりません。
`statement_start_offset` / `statement_end_offset` を使って
**該当ステートメントだけを切り出す**ように書き換えなさい。
そのうえで次の3点を説明しなさい。

1. なぜオフセットを **2で割る** のか
2. `statement_end_offset` が **-1** のときは何を意味し、どう処理するのか
3. なぜ `LEN` ではなく **`DATALENGTH`** を使うのか

**Q7.** 同じ骨格のクエリで、次の3つのランキングをそれぞれ出しなさい。

1. **論理読み取り合計** の上位10
2. **実行回数** の上位10
3. **1回あたりの平均論理読み取り** の上位10(ただし実行回数が5回以上のものに限る)

そのうえで、**1 と 3 で顔ぶれがどう変わるか** を確認し、
**「サーバー全体を軽くしたい」ときと「特定の画面が遅い」ときで、どちらを見るべきか** を説明しなさい。

**Q8.** `sys.dm_exec_query_stats` を **`query_hash` で集約**し、
「実質同じだがリテラルだけ違うクエリ」の合計負荷を出しなさい。
`プラン数`(その `query_hash` に対応するプランの本数)も出力し、
**プラン数が多いことが何を意味するか** を説明しなさい。

**Q9.** ブロッキングを実際に発生させて観測しなさい。

1. **W3** で `05_workload.sql` の **セクションC**(30秒ロック保持)を実行する
2. すぐに **W1** で **セクションD** を実行する(ブロックされる)
3. **W4** で、**ブロックされているセッションとブロック元** を一覧するクエリを実行する

出力には「被害者のSQL」と「**ブロック元のSQL**」の両方を含めること。
実行してみると **ブロック元の SQL が `sys.dm_exec_requests` からは取れない** はずです。
**その理由**と**回避方法**を答えなさい。

**Q10.** Q9 と同じ状況で、**`sys.dm_os_waiting_tasks`** から待機中のタスクを一覧しなさい。
`sys.dm_exec_requests` の情報と何が違うか、また
**`sys.dm_os_wait_stats` との使い分け** を説明しなさい。

**Q11.** **再帰CTE** を使って、**ブロッキングチェーンの先頭ブロッカー** を特定するクエリを書きなさい。
要件:

- ブロックの階層(レベル)が分かること
- `10 > 55 > 58` のような **連鎖の経路** が文字列で出ること
- レベル0(先頭ブロッカー)に印が付くこと
- 各セッションのログイン名・ホスト名・アプリ名・セッション状態が出ること
- **無限再帰への保険**を入れること

(ヒント: 「誰かをブロックしているが、自分は誰にもブロックされていない」セッションがアンカー)

**Q12.** ファイル別の IO 待ち時間を **2通り**の方法で測りなさい。

1. `sys.dm_io_virtual_file_stats` の **累積値**から、平均読み取り待ち(ms)と平均書き込み待ち(ms)を出す
2. **30秒間のスナップショット差分**から、同じ指標を「その30秒間だけ」について出す
   (30秒の間に W1/W3 で負荷を流しておくこと)

1 と 2 で値が違う理由を説明し、**どちらを障害調査で使うべきか** を答えなさい。

**Q13.** `dbo.OrdersBig` に次の2本の非クラスタ化インデックスを作りなさい。

- `IX_OrdersBig_OrderDate` … `(OrderDate)`
- `IX_OrdersBig_Status` … `(Status)`

作成後、**`IX_OrdersBig_OrderDate` を使うクエリだけを数回実行**し、
`IX_OrdersBig_Status` は一度も使わないでください。
そのうえで **「読み取り 0 なのに更新コストだけ払っているインデックス」を検出するクエリ** を書き、
`IX_OrdersBig_Status` が検出されることを確認しなさい。

さらに、**この結果だけを根拠に本番でインデックスを DROP してはいけない理由** を
最低4つ挙げなさい。

## チャレンジ

**Q14.** 欠落インデックスの提案を観察し、**鵜呑みにしない**練習をします。

1. Q13 で作ったインデックスを **いったん両方 DROP** する
2. 次のようなクエリを何度か実行して、オプティマイザに提案を溜めさせる
   - `CustomerId` で絞り、`OrderDate` と `Amount` を返すクエリ
   - `Status` と `OrderDate` の範囲で絞り、`Amount` を集計するクエリ
3. `sys.dm_db_missing_index_details` / `_groups` / `_group_stats` を結合し、
   **改善見込みスコア順**に提案を一覧するクエリを書く
   (スコア = `avg_total_user_cost × avg_user_impact/100 × (user_seeks + user_scans)`)
4. 出力に **提案どおりの `CREATE INDEX` 文の草案** も組み立てて表示する

そのうえで、次に答えなさい。

- 提案された列の **順序** は妥当か。18章の「等値 → 範囲」「選択度が高い列を先に」に照らして検討しなさい
- 提案された `INCLUDE` は妥当か。過剰ではないか
- **2つの提案を1本のインデックスに統合**できないか検討し、**自分で設計した1本**を作りなさい
- 作成前後の**論理読み取り数**を比較して、効果を数字で示しなさい
- **`sys.dm_db_missing_index_*` は「インデックスを作ると消える」** ことを確認しなさい

**Q15.** シングルユース プランの肥大化を再現し、検出し、**影響範囲を限定して**掃除しなさい。

1. 現在の「シングルユース アドホックプランの数・サイズ・全体に占める比率」を測る
2. **パラメーター化されていない SQL を200本**生成して実行する
   (`WHERE CustomerId = 1`、`= 2` … のようにリテラルを変えた `SELECT` を動的SQLで流す)
3. もう一度 1 を測り、**増えたことを確認**する
4. どんな SQL がキャッシュに溜まったかを、`usecounts = 1` かつ `objtype = 'Adhoc'` で一覧する
5. **同じことを `sp_executesql` でパラメーター化して200本**実行し、
   **プランが1本しか増えない**ことを確認する
6. 溜まったゴミを掃除する。ただし **`DBCC FREEPROCCACHE`(引数なし)は使わないこと**。
   影響範囲を限定した方法を **3つ以上**挙げ、そのうち1つを実行しなさい

**Q16.** `sys.dm_db_index_physical_stats` の **3つのモード**を比較しなさい。

1. `dbo.OrdersBig` に対して `LIMITED` / `SAMPLED` / `DETAILED` をそれぞれ実行する
2. `SET STATISTICS TIME ON` で **実行時間**を記録し、コストの差を数字で示す
3. **モードによって取れる列が違う**ことを確認する(どの列が `LIMITED` では NULL / 0 になるか)
4. **本番環境で `DETAILED` を全オブジェクトに対して実行してはいけない理由** を説明しなさい

**Q17.**(**総合**)次のシナリオに、**この章と 18 / 23 / 24 章の知識を組み合わせて**答えなさい。
クエリを書く必要はありませんが、**各段階で使う DMV / 機能の名前を必ず具体的に挙げる**こと。

> 朝9時に「基幹システムの受注検索画面がここ数日だけ極端に遅い」と連絡が来た。
> サーバーは3か月前から再起動していない。Query Store は有効になっている。
> 今も遅い状態が続いている。

1. **最初に確認すること**は何か。なぜそこから始めるのか
2. 「今」の状態を掴むために、どの DMV をどの順で叩くか
3. 「ここ数日だけ」という時間軸の情報は、どこから取るのが正しいか。**なぜ DMV では不十分なのか**
4. 原因が「プランが変わったこと」だと分かった場合、次に何を見るか
5. 修正後、**効果をどう証明するか**(何の数字を、いつと比較するか)

**Q18.**(**必須の後片付け**)この演習で作成したものをすべて削除し、環境を元に戻しなさい。

- `dbo.OrdersBig` の非クラスタ化インデックスをすべて削除し、`PK_OrdersBig` だけの状態に戻す
- Q14 で自分が設計したインデックスも削除する
- Q15 で作成した一時オブジェクトがあれば削除する
- W1〜W3 の負荷スクリプトがすべて停止していること、
  **未完了トランザクションが残っていないこと**(`@@TRANCOUNT` と `sys.dm_tran_active_transactions`)を確認する
- 必要なら `05_workload.sql` の **【後片付け】セクション**で `dbo.WorkloadTest` を削除する
- 最後に、インデックスが本当に残っていないことを `sys.indexes` で確認する
