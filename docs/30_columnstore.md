# 30 列ストアインデックスとバッチモード

> **このトピックのゴール**: 同じ集計クエリが、行ストアと列ストアで **10〜100 倍** 変わることを
> 自分の手で計測し、**なぜそうなるか**(列単位の格納・セグメント除外・バッチモード)を
> 内部構造から説明できるようになる。さらに **効かないときに何を疑うか** を、
> `sys.column_store_segments` と `sys.dm_db_column_store_row_group_physical_stats` で切り分けられるようになる。
>
> **前提**: [29 結合アルゴリズムと並列処理](29_join_algorithms_parallelism.md) までを済ませていること。
> **さらに、この章は `sample-db/04_analytics_data.sql` を実行して `dbo.SalesFact`(1000万行)を
> 作成済みであることが前提** です。まだなら先に実行してください(環境により 1〜3 分かかります)。

すべての例は先頭で `USE SalesLearning;` を実行済みとします。

```sql
-- 準備確認: 1000万行あることを確かめる
SELECT COUNT_BIG(*)  AS 行数,
       MIN(SaleDate) AS 最古,
       MAX(SaleDate) AS 最新
FROM   dbo.SalesFact;
```

`dbo.SalesFact` の構成(再掲):

| 列 | 型 | 内容 |
|---|---|---|
| `SaleId` | BIGINT | **クラスタ化主キー**。1〜10,000,000 の連番 |
| `SaleDate` | DATE | 2015-01-01〜2024-12-31。**`SaleId` にほぼ比例した日付順で格納されている** |
| `CustomerId` | INT | 1〜1000(合成。`dbo.Customers` とは無関係なので結合しない) |
| `ProductId` | INT | 1〜20(`dbo.Products` と結合可能) |
| `EmployeeId` | INT | 1〜13(`dbo.Employees` と結合可能) |
| `RegionId` | INT | 1〜8 |
| `Quantity` / `UnitPrice` / `Discount` / `Amount` | INT / DECIMAL | 数量・単価・割引率・金額 |

> ⚠️ **列ストアインデックスもパーティションも、まだ1つも作られていません**。
> この章と演習で自分の手で作り、行ストア版との差を計測します。

[18 インデックスと実行プラン](18_indexes_execution_plans.md) で扱った B木インデックスは、
**「大量の行の中から少数の行を素早く取り出す」**ための道具でした。
この章で扱う列ストアは、まったく逆の目的 —
**「大量の行を全部なめて集計する」**ための道具です。同じ「インデックス」という名前ですが、別物と考えてください。

## 1. 行ストアと列ストアの根本的な違い

### 1-1. 格納の向きが 90 度違う

**行ストア(rowstore)** は、1行ぶんの全列をひとかたまりにして 8KB ページに詰めます。

```
行ストア(8KB ページの中身)
┌──────────────────────────────────────────────────────────┐
│ [1, 2015-01-01, 501, 2, 3, 4, 5, 300, 0.10, 1350.00]      │ ← 1行目(全10列)
│ [2, 2015-01-01, 502, 3, 4, 5, 6, 400, 0.15, 2040.00]      │ ← 2行目(全10列)
│ [3, 2015-01-01, 503, 4, 5, 6, 7, 500, 0.20, 2800.00]      │ ← 3行目(全10列)
│ ...                                                       │
└──────────────────────────────────────────────────────────┘
```

**列ストア(columnstore)** は、**同じ列の値だけ**を縦にまとめて別々に格納します。

```
列ストア(列ごとに独立した「セグメント」)
 SaleId    : [1, 2, 3, 4, 5, ... ]          ← このかたまりだけ読める
 SaleDate  : [2015-01-01, 2015-01-01, ... ] ← このかたまりだけ読める
 CustomerId: [501, 502, 503, ... ]
 ...
 Amount    : [1350.00, 2040.00, 2800.00, ...] ← このかたまりだけ読める
```

### 1-2. なぜ集計クエリで劇的に効くのか

理由は3つあり、**掛け算で効きます**。

**(a) 必要な列だけ読める(I/O が列数ぶんの1になる)**

```sql
SELECT RegionId, SUM(Amount) AS 売上合計
FROM   dbo.SalesFact
GROUP  BY RegionId;
```

このクエリが必要としているのは `RegionId` と `Amount` の **2列だけ**です。
ところが行ストアでは、1行ぶんの 10 列すべてが同じページに載っているため、
**使わない 8 列も一緒に読まされます**。列ストアなら 2 列ぶんのセグメントだけ読めば済む。
これだけで I/O が **1/5 前後**になります。

> 💡 [01 SELECT の基礎](01_select_basics.md) の「`SELECT *` を避けよ」がここで最大の効果を発揮します。
> 列ストアでは **`SELECT` に書いた列の数がそのまま I/O 量**です。`SELECT *` は列ストアの利点を完全に捨てる行為です。

**(b) 圧縮率が桁違い(4 節)**

同じ列の値は **型も傾向もそろっている**ので、まとめて圧縮すると非常によく縮みます。
行ストアでは隣り合う値が「日付・整数・文字列・小数…」とバラバラなので、ここまでは縮みません。
実測で **行ストアの 1/5〜1/10** になるのが普通です。I/O が減るだけでなく、
**バッファプールに載る量が増える**(=物理読み取りが減る)効果もあります。

**(c) セグメント除外とバッチモード(5・6 節)**

述語に合わないかたまりを **丸ごと読み飛ばし**、残りを **900 行ずつまとめて処理**します。
これが最後のひと押しになります。

### 1-3. 逆に、列ストアが苦手なこと

```sql
SELECT * FROM dbo.SalesFact WHERE SaleId = 5000000;   -- 1行だけ欲しい
```

これは **行ストアの独壇場**です。B木なら 3〜4 ページで届きます。
列ストアには B木がないので、**10 列ぶんのセグメントをそれぞれ開いて 1 行を組み立て直す**羽目になります。
「1行を取り出す」のに最も向かない構造なのです(11 節)。

**列ストア = 少数の列 × 大量の行を集計する。行ストア = 大量の列 × 少数の行を取り出す。**
この一文がすべてです。

## 2. 内部構造 — ロウグループとセグメント

列ストアの用語は 2 つだけ覚えれば足ります。

| 用語 | 意味 |
|---|---|
| **ロウグループ (rowgroup)** | 行を最大 **1,048,576 行**(= 2^20)ずつ区切った、圧縮の単位 |
| **セグメント (segment)** | **1 ロウグループ × 1 列** ぶんのデータのかたまり。**読み書きの最小単位** |

```
                     ← 列 (10 列) →
        ┌──────┬──────┬──────┬─ ─ ─┬──────┐
 ロウ   │ Seg  │ Seg  │ Seg  │     │ Seg  │  ロウグループ 0 (1,048,576 行)
 グル   ├──────┼──────┼──────┼─ ─ ─┼──────┤
 ープ   │ Seg  │ Seg  │ Seg  │     │ Seg  │  ロウグループ 1 (1,048,576 行)
 (10)   ├──────┼──────┼──────┼─ ─ ─┼──────┤
  ↓     │ ...  │ ...  │ ...  │     │ ...  │
        └──────┴──────┴──────┴─ ─ ─┴──────┘
         SaleId SaleDate Cust..      Amount
```

- 1000万行なら `10,000,000 ÷ 1,048,576 ≈ 9.5` → **ロウグループは約 10 個**。
  列は 10 本なので、セグメントは **約 100 個**存在することになります。
- クエリが `RegionId` と `Amount` しか使わないなら、読むのは **2 列 × 10 ロウグループ = 20 セグメント**だけ。
  残り 80 セグメントには一切触りません。これが 1-2(a) の正体です。
- セグメントは内部的に **LOB(BLOB)として格納**されます。この事実は計測時に効いてきます(9 節)。

> ⚠️ **ロウグループは「1,048,576 行ちょうど」になるとは限りません**。
> メモリ不足・ディクショナリのサイズ上限・並列度など、さまざまな理由で途中で打ち切られます。
> **なぜ小さいのか**は `sys.dm_db_column_store_row_group_physical_stats` の
> `trim_reason_desc` 列が教えてくれます(10 節)。ここを見られるかどうかが実務での差になります。

## 3. デルタストアとタプルムーバー(102,400 行の壁)

### 3-1. 3 つの状態

列ストアは「圧縮してまとめる」構造なので、**1 行ずつの INSERT とは相性が悪い**。
そこで SQL Server は、**小さい INSERT を行ストア形式の一時置き場に貯める**仕組みを持っています。
これが **デルタストア (delta store)** です。

ロウグループの状態は次の 4 つです(`state_desc` 列の値)。

| 状態 | 意味 | 実体 |
|---|---|---|
| **OPEN** | まだ行を受け付けている途中 | **デルタストア**(B木の行ストア) |
| **CLOSED** | 1,048,576 行に達し、圧縮待ち | デルタストア(受付終了) |
| **COMPRESSED** | 列ストア形式に圧縮済み | **本来の列ストア** |
| **TOMBSTONE** | 圧縮済みになった元デルタストア。削除待ち | ほぼ空 |

```
   小さい INSERT              1,048,576 行           タプルムーバー
        │                        到達                  (約5分ごと)
        ▼                          │                       │
   ┌─────────┐                     ▼                       ▼
   │  OPEN   │ ───────────→ ┌──────────┐ ──────→ ┌──────────────┐
   │(デルタ) │              │  CLOSED  │         │ COMPRESSED   │
   └─────────┘              └──────────┘         │  (列ストア)  │
                                                  └──────────────┘
   大きい一括ロード(102,400行以上)
        └──────────────────────────────────────────────→ 直接ここへ
```

### 3-2. なぜ 102,400 行未満の INSERT はデルタストアに入るのか

**一括ロード(bulk load)のしきい値が 102,400 行**だからです。

- `BULK INSERT` / `bcp` / `INSERT ... SELECT` に **`WITH (TABLOCK)`** を付けたもの(2016+)は
  **一括ロード**として扱われます。
- そのバッチが **102,400 行以上**なら、**デルタストアを経由せず直接 COMPRESSED ロウグループ**が作られます。
- **102,400 行未満**なら、圧縮しても効率が悪い(小さすぎて圧縮率が出ず、セグメントが細切れになる)ので、
  **デルタストアに入れて、後で 1,048,576 行たまってからまとめて圧縮**します。

つまり 102,400 は **「これ以下のかたまりを単独で圧縮しても割に合わない」というしきい値**です。
1,048,576 の約 1/10。これを下回るロードを繰り返すと、
**デルタストア(=ただの行ストア)にデータが溜まり続け、列ストアの利点がまったく出ません**。

> ⚠️ **実務で最も多い「列ストアにしたのに速くならない」の原因がこれです。**
> ETL で 1 万行ずつ 100 回 INSERT すると、100 万行すべてがデルタストアに入ります。
> **バッチサイズを 102,400 行以上(理想は 1,048,576 行)にそろえ、`WITH (TABLOCK)` を付ける**。
> これだけで結果が変わります。

### 3-3. タプルムーバー

**タプルムーバー (tuple mover)** は、**CLOSED になったロウグループを圧縮する**バックグラウンド処理です。

- 既定では **約 5 分ごと**に起動します。つまり CLOSED になってもすぐには圧縮されません。
- **OPEN のロウグループには触りません**。1,048,576 行に達していないデルタストアは、
  放っておいても永遠に圧縮されないということです。
- 待ちたくないときは **手動で圧縮を促します**(10 節)。

```sql
-- OPEN / CLOSED のロウグループも含めて、今すぐ全部圧縮する(2016+)
ALTER INDEX CCI_SalesFactCS ON dbo.SalesFactCS
    REORGANIZE WITH (COMPRESS_ALL_ROW_GROUPS = ON);
```

> 💡 SQL Server 2019 以降のタプルムーバーは、**小さい COMPRESSED ロウグループを自動的に併合する
> バックグラウンド マージ**も行います(それ以前は手動 `REORGANIZE` が必須でした)。

## 4. 圧縮 — なぜそこまで縮むのか

列ストアは 1 セグメント(= 1 列 × 1 ロウグループ)ごとに、次を順に適用します。

1. **値のエンコード** … ディクショナリ(値の辞書化)、または最小値からのオフセット化。
   `RegionId` は 1〜8 の 8 種類しかないので、辞書番号 3bit で表現できます。
2. **並べ替えの最適化(Vertipaq 最適化)** … 圧縮率が上がるように行を入れ替える。
3. **Run-Length Encoding / bit-packing** … 同じ値の連続をまとめる。
4. **最終圧縮**。

同じ列の値は **型も桁数も傾向もそろっている**ため、この一連の処理が非常によく効きます。

```sql
-- 行ストア版と列ストア版のサイズを比べる(演習で dbo.SalesFactCS を作った後に実行)
SELECT OBJECT_NAME(p.object_id)          AS テーブル,
       i.type_desc                       AS 種別,
       SUM(ps.used_page_count) * 8 / 1024 AS 使用MB,
       SUM(ps.row_count)                 AS 行数
FROM   sys.dm_db_partition_stats AS ps
JOIN   sys.partitions AS p ON p.partition_id = ps.partition_id
JOIN   sys.indexes    AS i ON i.object_id = p.object_id AND i.index_id = p.index_id
WHERE  p.object_id IN (OBJECT_ID('dbo.SalesFact'), OBJECT_ID('dbo.SalesFactCS'))
GROUP  BY p.object_id, i.type_desc
ORDER  BY テーブル;
```

- `dbo.SalesFact`(行ストア)が **500〜700MB 程度**なのに対し、
  列ストア版は **50〜120MB 程度**に収まるのが典型です(環境・データにより前後する目安)。

### ARCHIVE 圧縮

さらに縮めたいときは **`COLUMNSTORE_ARCHIVE`** を指定できます。

```sql
-- 作成時に指定
CREATE CLUSTERED COLUMNSTORE INDEX CCI_SalesFactCS
    ON dbo.SalesFactCS
    WITH (DATA_COMPRESSION = COLUMNSTORE_ARCHIVE);

-- 後から特定のパーティションだけ切り替えることもできる
ALTER INDEX CCI_SalesFactCS ON dbo.SalesFactCS
    REBUILD PARTITION = 1 WITH (DATA_COMPRESSION = COLUMNSTORE_ARCHIVE);
```

| | `COLUMNSTORE`(既定) | `COLUMNSTORE_ARCHIVE` |
|---|---|---|
| サイズ | 基準 | さらに **20〜40% 小さい** |
| 読み取り CPU | 基準 | **重い**(展開コストが増える) |
| 向く用途 | 日常的に集計する現用データ | **めったに読まない古い年度** |

> ⚠️ ARCHIVE 圧縮は **CPU との交換**です。全体に一律で掛けるのは悪手。
> [31 パーティショニング](31_partitioning.md) と組み合わせて
> **「古いパーティションだけ ARCHIVE」**にするのが定石です。

## 5. セグメント除外 (segment elimination) — この章の最重要ポイント

### 5-1. 仕組み

**各セグメントは、自分が持っている値の最小値と最大値をメタデータとして持っています。**

クエリに `WHERE SaleDate >= '2024-01-01'` という述語があると、SQL Server は
セグメントを開く**前に** min/max を見て、
**「このセグメントの最大値は 2016-03-05 だ。条件に合う行は 1 行も無い」→ 丸ごとスキップ**
と判断できます。これが **セグメント除外(= ロウグループ除外)** です。

```
 SaleDate セグメントの min/max
 ┌────────────────────────────────────────────────┐
 │ RG0: 2015-01-01 〜 2016-01-19  → スキップ ✂    │
 │ RG1: 2016-01-19 〜 2017-02-06  → スキップ ✂    │
 │ ...                                             │
 │ RG8: 2023-05-04 〜 2024-05-22  → 読む           │  WHERE SaleDate >= '2024-01-01'
 │ RG9: 2024-05-22 〜 2024-12-31  → 読む           │
 └────────────────────────────────────────────────┘
        10 セグメント中 8 個を「開かずに」捨てられる
```

これは B木の Seek と違い、**インデックスキーが要りません**。
**すべての列**が min/max を持っているので、どの列の述語でも除外が効く可能性があります。

### 5-2. しかし ——「データが並んでいないと効かない」

ここが決定的です。**セグメント除外は、その列の値がロウグループ間で偏っていて初めて効きます。**

`dbo.SalesFact` の `CustomerId` は 1〜1000 が全行にわたって循環しています。
つまり **どのロウグループも CustomerId 1〜1000 を全部含んでいる**。
すると `WHERE CustomerId = 500` に対して、
**全 10 セグメントの min=1, max=1000** となり、**1 つも除外できません**。

一方 `SaleDate` は `SaleId` に比例して並んでいるので、
**ロウグループごとに日付の範囲が綺麗に分かれています**。だから除外が効く。

### 5-3. 伏線回収 — なぜ `04_analytics_data.sql` は日付を `SaleId` に比例させたのか

`sample-db/04_analytics_data.sql` を開くと、データ生成部にこう書かれています。

```sql
    /* ★重要: 日付を n に比例させ、ほぼ日付順に格納する。
       列ストアのセグメント除外は「セグメント内の値の範囲が狭いこと」で効く。
       日付をランダムに散らすと全セグメントが全期間を含み、除外が一切効かない。 */
    DATEADD(DAY, (n - 1) / @PerDay, '2015-01-01'),
```

**これは「本物のファクト表を模した意図的な設計」です。**
現実の売上ファクト表も、日々の取引が発生順に積み上がるので **自然に日付順**になります。
逆に、既存データをランダムな順序でロードしてしまうと —
たとえば `ORDER BY NEWID()` で入れ直したり、`CustomerId` 順にソートして入れたりすると —
**日付の除外は永久に効かなくなります**。

> ⚠️ **列ストアの性能の半分は「どの順序でロードしたか」で決まります。**
> インデックス定義には順序を書く場所がありません(2019 以前)。
> 順序を制御する手段は **ロードするときのデータの並び順だけ**です。
> 「列ストアを作ったのに遅い」ときは、**まず並び順を疑う**。

対策は 3 つあります。

1. **ロード時に、よく絞る列(たいていは日付)で `ORDER BY` してから入れる**。
2. **CCI をその順序で構築する**(構築時は `MAXDOP = 1` にする。8-3 節)。
3. **SQL Server 2022 以降なら `ORDER` 句を使う**(下記)。

```sql
-- SQL Server 2022 (16.x) 以降: 順序付きクラスター化列ストアインデックス
CREATE CLUSTERED COLUMNSTORE INDEX CCI_SalesFactCS
    ON dbo.SalesFactCS
    ORDER (SaleDate)
    WITH (DROP_EXISTING = ON, MAXDOP = 1);
```

> ⚠️ `ORDER` は **完全なソートを保証しません**(メモリの都合で近似ソートになります)。
> それでも min/max の重なりは大きく減るので、効果は十分あります。

### 5-4. `sys.column_store_segments` で min/max を確認する

```sql
-- SaleId 列(BIGINT)のセグメントごとの値の範囲を見る
SELECT rg.row_group_id                  AS ロウグループ,
       rg.state_desc                    AS 状態,
       rg.total_rows                    AS 行数,
       c.name                           AS 列名,
       s.min_data_id                    AS 最小,
       s.max_data_id                    AS 最大,
       s.on_disk_size / 1024            AS セグメントKB
FROM   sys.column_store_segments AS s
JOIN   sys.partitions AS p
       ON  p.hobt_id = s.hobt_id
JOIN   sys.indexes AS i
       ON  i.object_id = p.object_id AND i.index_id = p.index_id
JOIN   sys.columns AS c
       ON  c.object_id = p.object_id AND c.column_id = s.column_id
JOIN   sys.column_store_row_groups AS rg
       ON  rg.object_id    = p.object_id
       AND rg.index_id     = p.index_id
       AND rg.row_group_id = s.segment_id
WHERE  p.object_id = OBJECT_ID('dbo.SalesFactCS')
  AND  c.name IN (N'SaleId', N'CustomerId')
ORDER  BY c.name, rg.row_group_id;
```

読み方:

- **`SaleId`** … `1〜1048576` / `1048577〜2097152` / … と **綺麗に分かれる**。→ 除外が効く。
- **`CustomerId`** … どのロウグループも `1〜1000`。**全部重なっている**。→ 除外が一切効かない。

これが 5-2 節の話を **数字で見せた形**です。

> ⚠️ `min_data_id` / `max_data_id` は **内部表現の整数**です。
> `INT` / `BIGINT` 列ならほぼ値そのものですが、`base_id` / `magnitude` が `-1` 以外のときは
> オフセット表現になり、`DATE` や文字列列では別の内部エンコードになります。
> **厳密な値の復元にこだわらず、「範囲が分かれているか、重なっているか」を見る**のが実用的な使い方です。
> 除外が本当に効いたかどうかの **決定的な証拠は、次の `SET STATISTICS IO` の出力**です。

### 5-5. 除外が効いたことを「測る」

列ストアに対する `SET STATISTICS IO ON` は、**行ストアには出ない専用の行**を出力します。

```sql
SET STATISTICS IO ON;

-- ① 日付で絞る → 除外が効く
SELECT SUM(Amount) AS 売上合計
FROM   dbo.SalesFactCS
WHERE  SaleDate >= '2024-01-01' AND SaleDate < '2025-01-01';

-- ② 顧客で絞る → 除外が効かない(全ロウグループを読む)
SELECT SUM(Amount) AS 売上合計
FROM   dbo.SalesFactCS
WHERE  CustomerId = 500;

SET STATISTICS IO OFF;
```

メッセージ タブにこう出ます。

```
テーブル 'SalesFactCS'。セグメント読み取り数 2、セグメントのスキップ数 8。   ← ①
テーブル 'SalesFactCS'。セグメント読み取り数 10、セグメントのスキップ数 0。  ← ②
```

- **`セグメントのスキップ数` (segment skipped) が、セグメント除外の効き具合そのもの**です。
- ① は 10 個中 8 個を読み飛ばした。② は 1 個も飛ばせなかった。
  **同じテーブル・同じ 1000万行なのに、述語の列が違うだけでこの差**が出ます。

### 5-6. 判断基準

| 見えた数字 | 疑うこと |
|---|---|
| `セグメントのスキップ数 = 0` なのに述語で強く絞っているはず | **ロード順序**が述語列に沿っていない(5-3 節)。並べ替えて作り直す |
| ロウグループ数が想定(行数 ÷ 1,048,576)より **明らかに多い** | 小さいロウグループが乱立。`trim_reason_desc` を確認(10 節) |
| `state_desc = OPEN` の行が多い | デルタストアに溜まっている。バッチサイズと `TABLOCK` を確認(3-2 節) |
| 除外は効いているのに遅い | 述語が非 SARGable、または結合・並列度の問題([29](29_join_algorithms_parallelism.md)) |

> ⚠️ セグメント除外は **`WHERE 列 = 値` の形**でこそ効きます。
> `WHERE YEAR(SaleDate) = 2024` のように **列を関数で包むと、min/max との比較ができなくなり除外が消えます**。
> [18 章](18_indexes_execution_plans.md) の SARGability は、列ストアでもそのまま生きています。

## 6. バッチモード実行

### 6-1. 行モードとバッチモード

従来の実行モデル(**行モード / row mode**)は、演算子どうしが **1 行ずつ**データを受け渡します。
1000万行を集計するなら、演算子間で **1000万回**の呼び出しが発生します。

**バッチモード (batch mode)** は、**約 900 行をひとかたまり(バッチ)にして一度に受け渡す**実行モデルです。

| | 行モード | バッチモード |
|---|---|---|
| 受け渡し単位 | 1 行 | **約 900 行** |
| 呼び出し回数(1000万行) | 1000万回 | **約 11,000 回** |
| CPU 命令 | 行ごとに分岐 | **SIMD で列方向に一括処理** |
| メモリ表現 | 行の構造体 | **列指向のベクター** |

- 呼び出しのオーバーヘッドが **1/900** になるだけでなく、
  バッチの中身が列指向なので **CPU のベクター命令(SIMD)** をそのまま使えます。
- さらに **集計プッシュダウン (aggregate pushdown)**(2016+)が効くと、
  `SUM` / `COUNT` / `MIN` / `MAX` を **スキャン演算子の内部で直接計算**してしまい、
  上位の演算子には集計済みの少数行しか流れません。

**行モード → バッチモードだけで CPU 時間が 5〜20 倍変わる**ことは珍しくありません。

### 6-2. プランで「実際の実行モード」を確認する

SSMS で **`Ctrl` + `M`(実際の実行プランを含める)** を ON にして実行し、
**Columnstore Index Scan** や **Hash Match (Aggregate)** の演算子を右クリック →
**[プロパティ]** を開きます。

| プロパティ | 見るポイント |
|---|---|
| **推定実行モード** | オプティマイザが選んだモード(`Row` / `Batch`) |
| **実際の実行モード** | **本当に使われたモード。ここが `Batch` かどうかがすべて** |
| **実際の行数(バッチ)** | 流れたバッチ数。`実際の行数 ÷ バッチ数 ≒ 900` になる |

> ⚠️ **推定は `Batch` なのに実際は `Row`** ということが起こり得ます。
> メモリ不足でバッチモードのハッシュテーブルが確保できなかった場合などです。
> **必ず「実際の実行モード」を見てください。**

演算子ごとにモードは異なります。**プランの一部だけがバッチモード**というのが普通で、
**行モードとバッチモードの境目には変換のコストが掛かります**。
プランの下流(左側)まで `Batch` が続いているほど良い、と覚えてください。

### 6-3. バッチモードが選ばれない典型的な理由

- 対象の行数が少なすぎる(オプティマイザが行モードで十分と判断)。
- プランが **直列**で、かつ古いバージョン(2014 以前は **並列プランでしかバッチモードにならない**)。
- **`CURSOR`、スカラー UDF、`OUTER APPLY` の一部**など、バッチモード非対応の要素が混ざっている。
  → [16 ストアドプロシージャとユーザー定義関数](16_stored_procedures.md) のスカラー UDF は特に要注意
    (2019 以降のインライン化が効かない UDF はプラン全体を行モードに落とします)。
- メモリ許可(memory grant)が足りない。

### 6-4. 行ストアに対するバッチモード(Batch Mode on Rowstore, 2019+)

**SQL Server 2019 (15.x) 以降**、**列ストアインデックスが1つも無くても**、
行ストアのテーブルに対してバッチモードが使えるようになりました。

条件:

- **データベース互換性レベルが 150 以上**であること。
- オプティマイザのヒューリスティックを満たすこと。おおむね
  **テーブルが 131,072 行(= 1,048,576 ÷ 8)以上**あり、集計・結合を含む分析系の形をしていること。

```sql
-- 互換性レベルの確認(変更はしない。確認だけ)
SELECT name AS DB名, compatibility_level AS 互換性レベル
FROM   sys.databases
WHERE  name = N'SalesLearning';
```

ヒントで明示的に制御できます。**設定を変えずに効果だけ確かめられる**ので、検証にはこちらを使ってください。

```sql
-- 行ストアの dbo.SalesFact に対して、バッチモードを禁止して実行
SELECT RegionId, SUM(Amount) AS 売上合計, COUNT_BIG(*) AS 件数
FROM   dbo.SalesFact
GROUP  BY RegionId
OPTION (USE HINT('DISALLOW_BATCH_MODE'));

-- 逆に、ヒューリスティックを無視して積極的に使わせる
SELECT RegionId, SUM(Amount) AS 売上合計, COUNT_BIG(*) AS 件数
FROM   dbo.SalesFact
GROUP  BY RegionId
OPTION (USE HINT('ALLOW_BATCH_MODE'));
```

> ⚠️ **互換性レベルはデータベース全体の設定**です。学習のために変えるなら
> **必ず元に戻してください**。現在値を控えたうえで:
> ```sql
> -- 元の値が 150 だった場合の戻し方
> ALTER DATABASE SalesLearning SET COMPATIBILITY_LEVEL = 150;
> ```
> 本章の演習では **互換性レベルは変更せず、`USE HINT` だけで検証**します。

**重要な線引き**: 行ストアのバッチモードは **実行モデルだけ**を借りたものです。
**列単位の I/O 削減も、圧縮も、セグメント除外も付いてきません**。
「2019 だからもう列ストアは要らない」は誤りで、**効果の大きさは列ストアのほうが桁で上**です。

## 7. 種類と使い分け — CCI と NCCI

| | **クラスター化列ストア (CCI)** | **非クラスター化列ストア (NCCI)** |
|---|---|---|
| 実体 | **テーブル本体そのもの**が列ストア | 行ストア表に**追加**する副本 |
| 本数 | 1 テーブルに 1 本 | 1 テーブルに 1 本 |
| 記憶域 | 行ストアのコピーを持たない(**最も小さい**) | **データが二重に持たれる**(容量増) |
| 更新 | 可(2014+) | **2016 以降で更新可**(2012/2014 は読み取り専用) |
| 主な用途 | **分析専用のファクト表・DWH** | **HTAP**(業務処理と分析の併用) |

### 7-1. CCI — 分析専用テーブル

分析しかしないテーブルは、迷わず **CCI** です。
本体が列ストアなので **行ストアの重複を持たず、最も容量効率が良い**。

```sql
CREATE CLUSTERED COLUMNSTORE INDEX CCI_SalesFactCS ON dbo.SalesFactCS;
```

- CCI にはキー列がありません(全列が対象なので指定不要)。
- **2016 以降は、CCI のテーブルに非クラスター化 B木インデックスを追加できます**。
  「基本は分析だが、たまに 1 行のピンポイント検索も要る」という場合に有効です。

```sql
-- CCI のテーブルに、点検索用の B木インデックスを併設する(2016+)
CREATE NONCLUSTERED INDEX IX_SalesFactCS_SaleId ON dbo.SalesFactCS (SaleId);
```

### 7-2. NCCI — HTAP(業務+分析の併用)

**既存の業務テーブル(行ストア)を触らずに、分析だけ速くしたい**ときが NCCI の出番です。

```sql
-- 行ストア表 dbo.OrdersBig はそのまま。分析用の列だけを列ストアで持つ
CREATE NONCLUSTERED COLUMNSTORE INDEX NCCI_OrdersBig
    ON dbo.OrdersBig (OrderDate, CustomerId, Status, Amount);
```

- 業務側の `WHERE OrderId = ?` は今までどおり B木でシークする。
- 分析側の `GROUP BY` は NCCI をバッチモードでスキャンする。
  **1 つのテーブルで OLTP と分析を両立**させる —— これが **HTAP (Hybrid Transactional/Analytical Processing)** です。
- 代償は **容量と更新コスト**。列ストアぶんのデータが増え、更新のたびに両方を保守します。

### 7-3. フィルター選択された NCCI

HTAP の切り札です。**「更新が終わって二度と変わらない行」だけ**を列ストアに載せます。

```sql
-- 完了済みの注文だけを列ストアに持つ(2016+)
CREATE NONCLUSTERED COLUMNSTORE INDEX NCCI_OrdersBig_Done
    ON dbo.OrdersBig (OrderDate, CustomerId, Amount)
    WHERE Status = N'完了';
```

なぜ効くのか:

- 業務中の「熱い」行(`N'保留'`)は **頻繁に更新される** → 列ストアに入れると更新コストが跳ね上がる。
- 完了済みの「冷えた」行(95%)は **もう更新されない** → 列ストアの純粋な利点だけを享受できる。
- **更新負荷を避けつつ、分析対象の大半をカバー**できる。これが「ホット/コールド分離」の考え方です。

> ⚠️ フィルター選択されたインデックスは、**クエリの条件がインデックスの `WHERE` を包含している**
> ときにしか使われません。`WHERE Status = N'完了' AND ...` と書く必要があります。
> [18 章 8 節](18_indexes_execution_plans.md) のフィルター選択されたインデックスと同じ制約です。

## 8. 作り方

### 8-1. 既存テーブルを列ストアに変える

```sql
-- 行ストア表を、そのまま CCI に置き換える(元の B木は消える)
CREATE CLUSTERED COLUMNSTORE INDEX CCI_名前 ON dbo.テーブル
    WITH (DROP_EXISTING = ON);
```

### 8-2. 行ストア表からコピーして作る(この章で使う手順)

**元のテーブルを壊さずに比較したい**ので、本章と演習ではコピーを作ります。

```sql
-- ① 行ストアのコピーをヒープとして作る(SELECT INTO)
DROP TABLE IF EXISTS dbo.SalesFactCS;

SELECT SaleId, SaleDate, CustomerId, ProductId, EmployeeId, RegionId,
       Quantity, UnitPrice, Discount, Amount
INTO   dbo.SalesFactCS
FROM   dbo.SalesFact
ORDER  BY SaleId;               -- ★ 日付順に並べて入れる(5-3 節)

-- ② クラスター化列ストアインデックスを作る
CREATE CLUSTERED COLUMNSTORE INDEX CCI_SalesFactCS
    ON dbo.SalesFactCS
    WITH (MAXDOP = 1);          -- ★ 順序を保つため(8-3 節)
```

- `SELECT INTO` は **最小ログ記録**が効くので、`INSERT ... SELECT` より高速です
  (復旧モデルが単純/一括ログの場合)。1000万行で 1〜3 分程度。
- `SELECT *` ではなく列を明示しているのは、[01 章](01_select_basics.md) の作法どおりです。

> ⚠️ **`SELECT INTO` の `ORDER BY` は物理的な格納順を保証する仕様ではありません**
> (ヒープには順序の概念がないため)。それでも実際には
> クラスタ化インデックスのスキャン順で入るため、この用途では十分に機能します。
> **順序を確実にしたいなら、②の CCI 構築を `MAXDOP = 1` で行う**のが実質的な担保になります。

### 8-3. なぜ `MAXDOP = 1` なのか

CCI の構築を並列で行うと、**各スレッドが自分専用のロウグループを作ります**。

- 8 スレッドで 1000万行を構築すると、**各スレッドが 125 万行を担当** →
  1,048,576 行のロウグループ 1 つと、**20 万行程度の中途半端なロウグループ**が
  スレッドの数だけ生まれます。**小さいロウグループが 8 個も余分にできる**わけです。
- さらに、スレッドごとにスキャン範囲が入り乱れるため、**min/max の範囲が重なりやすくなります**。

`MAXDOP = 1` にすると、**1 スレッドが先頭から順に読み、1,048,576 行ずつ綺麗に詰めます**。
構築時間は延びますが、**その後の全クエリが速くなる**ので割に合います。

> 💡 **構築の並列度**と**クエリの並列度**は別物です。`MAXDOP = 1` で構築しても、
> クエリは並列・バッチモードで実行されます。混同しないこと。

## 9. 実測 — 行ストア版と列ストア版を比べる

**この章のハイライトです。** 演習で `dbo.SalesFactCS` を作ったら、
**まったく同じ集計クエリ**を両方に流して 3 つの数字を比べてください。

```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;

-- ① 行ストア(dbo.SalesFact)
SELECT YEAR(SaleDate) AS 年,
       RegionId       AS 地域,
       SUM(Amount)    AS 売上合計,
       COUNT_BIG(*)   AS 件数
FROM   dbo.SalesFact
GROUP  BY YEAR(SaleDate), RegionId
ORDER  BY 年, 地域;

-- ② 列ストア(dbo.SalesFactCS)— クエリ本文は 1 文字も違わない
SELECT YEAR(SaleDate) AS 年,
       RegionId       AS 地域,
       SUM(Amount)    AS 売上合計,
       COUNT_BIG(*)   AS 件数
FROM   dbo.SalesFactCS
GROUP  BY YEAR(SaleDate), RegionId
ORDER  BY 年, 地域;

SET STATISTICS IO OFF;
SET STATISTICS TIME OFF;
```

比較する 3 点(**環境により前後する目安**):

| 指標 | 行ストア | 列ストア | 見るところ |
|---|---|---|---|
| **論理読み取り数** | 60,000〜80,000 | **論理読み取り数はほぼ 0、`LOB 論理読み取り数` が数千** | 桁が 1〜2 つ落ちる |
| **CPU 時間** | 10,000〜40,000 ms | **500〜3,000 ms** | バッチモードの効果 |
| **経過時間** | 数秒〜十数秒 | **1 秒未満〜数秒** | 並列度でブレる |
| **実際の実行モード** | `Row`(2019+ なら `Batch` のことも) | **`Batch`** | プロパティで確認 |

### 9-1. 落とし穴: 列ストアの論理読み取り数は `LOB` 側に出る

```
テーブル 'SalesFact'。スキャン カウント 9、論理読み取り数 71234、物理読み取り数 0、
                       ... LOB 論理読み取り数 0、...

テーブル 'SalesFactCS'。スキャン カウント 4、論理読み取り数 0、物理読み取り数 0、
                        ... LOB 論理読み取り数 3812、...
テーブル 'SalesFactCS'。セグメント読み取り数 10、セグメントのスキップ数 0。
```

> ⚠️ **`論理読み取り数 0` を見て「I/O ゼロだ」と誤読しないこと。**
> セグメントは LOB として格納されるため、**列ストアの I/O は `LOB 論理読み取り数` に計上されます**。
> 比較するときは **行ストアの `論理読み取り数` ↔ 列ストアの `LOB 論理読み取り数`** を突き合わせます。

### 9-2. 効果が出やすいクエリ・出にくいクエリ

```sql
-- ◎ 大量行の集計。列も少ない。→ 列ストアの独壇場(10〜100倍)
SELECT ProductId, SUM(Amount) FROM dbo.SalesFactCS GROUP BY ProductId;

-- ◎ 日付で絞る集計。セグメント除外も効く。
SELECT SUM(Amount) FROM dbo.SalesFactCS
WHERE  SaleDate >= '2024-01-01' AND SaleDate < '2025-01-01';

-- △ SELECT * で全列を返す → 列ストアの利点(必要な列だけ)が消える
SELECT TOP (100) * FROM dbo.SalesFactCS;

-- ✗ 1 行のピンポイント検索 → 行ストア(B木)の圧勝
SELECT * FROM dbo.SalesFactCS WHERE SaleId = 5000000;
```

## 10. メンテナンス — 断片化を測って直す

列ストアの「断片化」は B木とは意味が違い、**次の 2 つ**です。

1. **削除された行**が残っている(列ストアの `DELETE` は **削除ビットマップに印を付けるだけ**で、
   セグメントからは消えない)。`UPDATE` は **削除 + 挿入**として処理されるので、これも溜まります。
2. **小さいロウグループ**が乱立している(3-2 節のデルタストア問題、8-3 節の並列構築問題)。

### 10-1. 状態を測る

```sql
SELECT rg.row_group_id                          AS ロウグループ,
       rg.state_desc                            AS 状態,
       rg.total_rows                            AS 総行数,
       rg.deleted_rows                          AS 削除済み行数,
       CAST(100.0 * rg.deleted_rows
            / NULLIF(rg.total_rows, 0) AS DECIMAL(5,1)) AS 削除率パーセント,
       rg.size_in_bytes / 1024 / 1024           AS サイズMB,
       rg.trim_reason_desc                      AS 打ち切り理由,
       rg.transition_to_compressed_state_desc   AS 圧縮経路
FROM   sys.dm_db_column_store_row_group_physical_stats AS rg
WHERE  rg.object_id = OBJECT_ID('dbo.SalesFactCS')
ORDER  BY rg.row_group_id;
```

`sys.dm_db_column_store_row_group_physical_stats` は **2016 以降**の DMV です。
(2014 では `sys.column_store_row_groups` を使いますが、`trim_reason` は取れません。)

**`trim_reason_desc` の読み方**(なぜ 1,048,576 行に届かなかったか):

| 値 | 意味 | 対処 |
|---|---|---|
| `NO_TRIM` | 満杯。**理想の状態** | — |
| `BULKLOAD` | 一括ロードのバッチが小さかった | **バッチサイズを 1,048,576 行に近づける**(3-2 節) |
| `MEMORY_LIMITATION` | メモリ不足で打ち切られた | メモリを増やす、`MAXDOP` を下げる |
| `DICTIONARY_SIZE` | 文字列列の辞書が上限に達した | カーディナリティの高い文字列列を外す |
| `RESIDUAL_ROW_GROUP` | 最後の端数。**正常** | — |
| `REORG` | `REORGANIZE` で強制圧縮された | — |
| `SPILLOVER` | デルタストアからあふれた | — |

> 💡 **`BULKLOAD` が並んでいたら、それが答えです。** ETL のバッチサイズを見直してください。
> `MEMORY_LIMITATION` なら、`MAXDOP` を下げるとスレッドあたりのメモリが増えて改善することがあります。

### 10-2. `REORGANIZE` と `REBUILD` の使い分け

| | `REORGANIZE` | `REBUILD` |
|---|---|---|
| 動作 | **小さい/削除の多いロウグループを併合**。OPEN/CLOSED を圧縮 | **全体を作り直す** |
| ロック | **オンライン**(業務を止めない) | 既定は**オフライン**(`ONLINE = ON` は 2019+ で CCI 対応) |
| コスト | 軽い。増分的 | 重い。全データを読み書き |
| 使いどき | **日常のメンテナンス。まずこちら** | 圧縮方式の変更、`REORGANIZE` で直らない致命的な断片化 |

```sql
-- ① 通常のメンテナンス(小さいロウグループの併合・削除行の除去)
ALTER INDEX CCI_SalesFactCS ON dbo.SalesFactCS REORGANIZE;

-- ② OPEN / CLOSED のデルタストアも今すぐ圧縮させる(2016+)
--    → 「ロードした直後に必ず実行する」のが定石
ALTER INDEX CCI_SalesFactCS ON dbo.SalesFactCS
    REORGANIZE WITH (COMPRESS_ALL_ROW_GROUPS = ON);

-- ③ 最終手段。圧縮方式を変えるときにも使う
ALTER INDEX CCI_SalesFactCS ON dbo.SalesFactCS REBUILD;
```

### 10-3. 実践的な判断基準

| 状態 | 判断 |
|---|---|
| `deleted_rows` の合計が総行数の **10% 未満** | 何もしない |
| `deleted_rows` が **10〜20%** | `REORGANIZE` |
| `deleted_rows` が **20% 超**、または `REORGANIZE` で減らない | `REBUILD`(パーティション単位が理想) |
| `state_desc = OPEN` のロウグループに大量の行 | **`REORGANIZE WITH (COMPRESS_ALL_ROW_GROUPS = ON)`** |
| 平均 `total_rows` が **10万行を大きく下回る** | ロード方法が間違っている。`trim_reason_desc` を見る |

> 💡 [31 パーティショニング](31_partitioning.md) と組み合わせると、
> **更新のあった直近パーティションだけ `REBUILD`** できます。
> 1000万行を毎晩まるごと再構築するのは現実的ではありません。**メンテナンスの単位を小さくすること**が本質です。

## 11. 向かないケース — 行ストアと併用する判断

列ストアが **不利になる**のは次の場合です。

| ケース | 理由 | 対処 |
|---|---|---|
| **1〜数行のピンポイント検索** | B木が無いのでセグメントを開いて組み立て直す | 行ストアの B木を併設(7-1 節) |
| **頻繁な単一行 UPDATE** | `UPDATE` = 削除ビットマップ + デルタストアへの挿入。断片化が進む | 更新の多い行は NCCI から外す(7-3 節) |
| **小口 INSERT の繰り返し** | 全部デルタストア行き(3-2 節) | バッチを 102,400 行以上にまとめる |
| **`SELECT *` が中心** | 全列を読むので列ストアの利点が消える | 列を絞る。または行ストアのまま |
| **行数が少ない**(数十万行未満) | ロウグループが 1 個も埋まらず、圧縮も除外も効かない | **行ストアで十分**。列ストアは百万行超から |
| **カーディナリティの高い文字列列が多い** | 辞書が肥大化し `DICTIONARY_SIZE` で打ち切られる | その列を列ストアから外す |

### 判断のフローチャート

```
そのテーブルは 100万行以上ある?
  │ いいえ → 行ストア(B木)で十分。ここで終わり。
  ▼ はい
分析(集計・スキャン)が主か、業務(点検索・更新)が主か?
  │ 分析が主 ────────────────→ CCI(7-1 節)
  │                              点検索も要るなら B木を併設
  ▼ 業務が主だが分析もしたい
更新が終わった「冷えた」行を条件で切り出せる?
  │ はい → フィルター選択された NCCI(7-3 節)  ★ 最も筋が良い
  ▼ いいえ
容量が 2 倍になっても許容できる?
  │ はい → NCCI(7-2 節)
  ▼ いいえ → 分析用テーブルを別に切り出して CCI(本章の演習の形)
```

> ⚠️ **「とりあえず全部 CCI にする」は失敗のもとです。**
> 行ストアと列ストアは **競合しません**。同じテーブルに両方置けます(7-1・7-2 節)。
> 「どちらか」ではなく **「どのアクセスパターンにどちらを当てるか」**で考えてください。

## よくあるつまずき

- **列ストアにしたのに速くならない** → まず `sys.dm_db_column_store_row_group_physical_stats` を見る。
  `state_desc = OPEN` ばかりならデルタストア(3-2 節)、
  `trim_reason_desc = BULKLOAD` ばかりならバッチサイズが小さい。
- **`セグメントのスキップ数` が常に 0** → **ロード順序**が述語列に沿っていない(5-3 節)。
  列ストアの性能はロード順序で決まります。
- **`論理読み取り数 0` を見て「I/O ゼロ」と誤読する** → 列ストアの I/O は
  **`LOB 論理読み取り数`** に出ます(9-1 節)。
- **`WHERE YEAR(SaleDate) = 2024` にしてしまう** → 列を関数で包むと **セグメント除外が消えます**。
  `>= '2024-01-01' AND < '2025-01-01'` に書き換える([18 章](18_indexes_execution_plans.md) と同じ話)。
- **`SELECT *` で計測して「効果が無い」と結論する** → 列ストアの I/O は列数に比例します。
  必要な列だけを書くこと。
- **CCI を既定の並列度で構築する** → 小さいロウグループが乱立し、min/max も重なる。
  **`WITH (MAXDOP = 1)`**(8-3 節)。
- **プランの「推定実行モード」だけ見て満足する** → 見るべきは **「実際の実行モード」**(6-2 節)。
- **少ない行数(数万行)のテーブルで試して差が出ないと言う** → ロウグループが 1 個も埋まりません。
  列ストアは **百万行超**からの道具です。
- **`DELETE` したのにサイズが減らない** → 削除ビットマップに印が付くだけ。
  `REORGANIZE` / `REBUILD` するまで領域は戻りません(10 節)。
- **2019 のバッチモードがあるから列ストア不要と考える** → 行ストアのバッチモードには
  **列単位 I/O も圧縮もセグメント除外も付いてきません**(6-4 節)。

## この章のまとめ

- **列ストアは「列ごとに縦に格納する」**。集計クエリで **必要な列だけ読める**ことが最大の利点。
  効果は「列を絞れる」×「圧縮が効く」×「セグメント除外」×「バッチモード」の**掛け算**。
- 内部構造は **ロウグループ(最大 1,048,576 行)** と **セグメント(列 × ロウグループ)** の 2 語で理解できる。
- **102,400 行未満の INSERT はデルタストア**に入る。これを下回るロードを繰り返すと
  **列ストアの利点がまったく出ない**。**バッチは 102,400 行以上、`WITH (TABLOCK)` を付ける**。
  状態は **OPEN → CLOSED → COMPRESSED**、圧縮するのは **タプルムーバー(約5分ごと)**。
- **セグメント除外が最重要**。各セグメントの **min/max** で読まずに捨てる。
  **データがその列で並んでいないと一切効かない**。
  `sample-db/04_analytics_data.sql` が `SaleDate` を `SaleId` に比例させているのはこのため。
  効き具合は **`SET STATISTICS IO` の「セグメントのスキップ数」**で測る。
- **バッチモード**は約 900 行をまとめて処理する実行モデル。プランの
  **「実際の実行モード = Batch」**を確認する。
  **2019 以降は行ストアにもバッチモード**が来たが、**列ストアの効果には及ばない**。
- **CCI = 分析専用テーブル**、**NCCI = 行ストア表に追加して HTAP**。
  **フィルター選択された NCCI** で「冷えた行だけ」を列ストアに載せるのが最も筋が良い。
- 作り方は **`SELECT INTO`(順序付き) → `CREATE CLUSTERED COLUMNSTORE INDEX ... WITH (MAXDOP = 1)`**。
- メンテナンスは **`sys.dm_db_column_store_row_group_physical_stats`** で測ってから。
  **`trim_reason_desc`** が「なぜ小さいのか」を教えてくれる。
  日常は **`REORGANIZE`**(必要なら `COMPRESS_ALL_ROW_GROUPS = ON`)、最終手段が **`REBUILD`**。
- **OLTP 的な点検索・単一行更新には向かない**。行ストアと **併用**して、
  アクセスパターンごとに使い分けるのが正解。
